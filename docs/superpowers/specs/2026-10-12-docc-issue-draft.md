**Title:** Static content (noscript) writes `picture` with `src` on `source`, an absolute checkout path, and no `src` on `img`

**Body:**

With `--transform-for-static-hosting` and `--experimental-transform-for-static-hosting-with-content`, the HTML that DocC writes inside `noscript` for each page has a fault in every image that has light and dark variants.

What DocC writes, for an image `window-result.png` with a `~dark` variant (path shortened):

```html
<picture>
  <source media="(prefers-color-scheme: dark)" src="/users/name/src/project/sources/module/module.docc/resources/window-result~dark@2x.png">
  <source media="(prefers-color-scheme: light)" src="/users/name/src/project/sources/module/module.docc/resources/window-result@2x.png">
  <img alt="...">
</picture>
```

Three problems:

1. Each `source` has `src`. Inside `picture`, a browser reads only `srcset`, so it ignores these.
2. The value is the file's path in the catalog on the machine that ran the build, in lower case, not its address in the built site (`images/<bundle>/window-result@2x.png`). So the published page also names a folder of the build machine.
3. The `img` has no `src`. A reader with JavaScript off, and a crawler, gets the alt text and no image.

An image with one variant has no `source`; its `img` gets the same wrong path as `src`.

Expected: `srcset` on each `source` with the site-relative address (and `2x` for `@2x` files), and an `img` whose `src` is the light variant.

**Reproduce:** a catalog with one article that shows one image with a light and a `~dark@2x` variant. Run `docc convert` with the two flags above and `--hosting-base-path`, then look inside the `noscript` element of the article's `index.html`.

Seen with the `docc` of Xcode 26.6 and Xcode 27.0 on macOS 27.2. A search of the Swift forums and the issues found no report.

Workaround we use: a post-build script that rewrites each `picture` from the files under `images/`.
